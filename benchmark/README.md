# Эталонный набор вопросов

30 вопросов для измерения качества, а не только скорости. До этого набора у проекта
были цифры латентности по фазам, но ни одной метрики правильности — то есть нельзя
было сказать, стало ли лучше после очередной правки.

## Что меряем

| Метрика | Как считается | Зачем |
|---|---|---|
| **recall@k** | доля вопросов, где `expect_article` попал в топ-k кандидатов ZIM-поиска | Главный подозреваемый в потерях. Кейс «кто мэр Тольятти → нашлась улица» — ровно про это: если статья не попала в топ-20, она потеряна навсегда, дальше по конвейеру её взять неоткуда |
| **fast-path hit-rate** | доля `infobox`-вопросов, отвеченных `FactoidAnswerer` | Показывает, какая часть нагрузки уходит за ~400 мс мимо модели |
| **accuracy** | доля ответов, совпавших с `expect_answer` | Появляется по мере верификации значений против конкретного ZIM |
| **false-fast-rate** | доля быстрых ответов из **неверной** статьи | Самая опасная ошибка: быстрый уверенный неправильный ответ хуже промаха |
| **wrong-field-rate** | доля быстрых ответов из верной статьи, но **не из того поля**, что в `expect_field` | Та же ошибка на уровень ниже. `matchByLabel` отвечает из любой метки карточки, а не из 13 подключённых свойств, — промахнуться строкой стало можно, и до 2026-08-31 это считалось чистым попаданием |
| **latency** | мс по фазам (поиск / чтение / prefill / decode) | Уже меряется, здесь фиксируется на едином наборе |

## Почему эталон — статья и поле, а не значение

`expect_article` и `expect_field` — стабильные утверждения: на вопрос про мэра Тольятти
должна найтись статья «Тольятти» и поле «Глава/мэр», и это не зависит ни от даты
снапшота ZIM, ни от того, что выдала наша система.

`expect_answer` намеренно оставлен `null` почти везде. Значения (мэр, население)
зависят от снапшота, а заполнять их тем, что вывела наша же система, — значит
получить циклический бенчмарк, который всегда показывает 100%. Заполняется по мере
ручной верификации против `wikipedia_ru_all_nopic_2026-01.zim`.

## Состав

| Категория | Штук | Что проверяет |
|---|---|---|
| `infobox` | 14 | Быстрый путь: ответ — одно поле карточки |
| `prose` | 8 | Один факт, но в теле статьи — нужен RAG |
| `list` | 5 | Перечисления — конвейер list-extraction |
| `multihop` | 5 | Две и более статьи, сравнение или вывод |

Набор специально включает случаи, на которых система уже спотыкалась:

- **ib10–ib12** — персоналии, у которых в ru.wiki инвертированный заголовок
  («Толстой, Лев Николаевич»). Прямая проверка разрешения сущности.
- **ib14** — заголовок со скобочным уточнителем («Сталкер (фильм)»): квалификатор
  должен приниматься.
- **pr08** — тот самый «какой автозавод там расположен», на котором ломалась
  кореференция местоимений.
- **mh03** — содержит «сравни», то есть обязан **не** уйти быстрым путём. Проверка
  стоп-листа `FactoidAnswerer`.

## Как прогонять

Два прогона, и они отвечают на разные вопросы.

**Поиск — `./benchmark/run_probe.sh [k] [serial]`.** Модель не трогается вовсе:
быстрый путь плюс отбор кандидатов ZIM, ~1 с на вопрос. Даёт recall@k,
hit-rate быстрого пути, false-fast-rate. Скорер — `score.py`.

**Полный ответ — `./benchmark/run_turn.sh [serial]`.** Настоящий ход чата со
всеми фазами, включая decode: ~30-60 с на вопрос, 20-30 минут на набор. Отвечает
на единственный вопрос «куда уходит время» — по фазам: попытка быстрого пути →
поиск в ZIM → чтение статей → prefill → decode. Скорер — `score_turn.py`.
Приложение должно быть на переднем плане на экране чата (вопрос приходит как
`SharedFlow`, из фона его никто не собирает), модель загружена, RAG включён.

Про правильность ответа `run_turn.sh` не говорит ничего — только про время.
Точность по-прежнему снимается глазами по строкам `Reply (...)` в `diag.log`.

При заполнении `expect_answer` указывать источник в `note`, чтобы было видно, что
значение верифицировано против ZIM, а не взято из вывода модели.
